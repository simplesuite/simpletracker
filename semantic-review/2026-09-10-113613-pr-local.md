# Mobile back-out cleanup for untouched tasks, notes, and projects

The mobile detail screens now intercept stack removal for header back, Android back, and gesture back, delete truly untouched records, and asynchronously save edited records before redispatching the original navigation action. Explicit delete actions set a bypass flag so their own `goBack()` does not re-enter the guard, and project-scoped note/task creation waits for store visibility before opening the editor. Watch for: new records opened before the store bridge exposes them can bypass cleanup (**High, likely**), the blank predicates discard non-title edits (**High, confirmed**), and a second back action can escape while the first async operation is pending (**Medium, confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

`beforeRemove` is the right interception point for the three stack exit mechanisms, and the successful path preserves the original navigation action with `navigation.dispatch(event.data.action)`. Explicit delete paths and task completion mark the guard as already handled before calling `goBack`; the task completion save behavior itself predates this back-out change and is noted separately below.

The cleanup decision is content-based rather than change-based. Notes are considered blank when title/body and, for lists, item count are empty; tasks only inspect title/body; projects inspect name, description, and attached records. That makes project assignment, note metadata/type changes, due-date/recurrence edits, and subtasks vulnerable to being discarded on back.

The project detail add flows wait for their records to enter the Zustand projections, but the top-level Notes, Tasks, and Projects list add flows navigate immediately after writing the Legend observable. Because those projections are rAF-batched, the detail listener can see no record and allow the first back action through without deleting the untouched record.

<details>
<summary>Issues (3)</summary>

1. **Record-not-visible cleanup bypass (High, likely)** — NotesListScreen, TasksListScreen, and ProjectsListScreen navigate immediately after creation, while each detail guard returns when its record selector is still empty. Wait for the record to become visible or make the detail screen own the pending-record cleanup before allowing any exit.
2. **Non-content edits classified as blank (High, confirmed)** — `NoteDetailScreen` ignores project/type/pin/archive changes and `TaskDetailScreen` ignores project, due, recurrence, and subtasks when deciding to delete on back. Base the decision on a complete dirty-state comparison, or save those fields before deleting.
3. **Concurrent back escapes the async guard (Medium, confirmed)** — Once the first exit sets `handlingBackRef`, later `beforeRemove` events return without preventing removal. Disable/reject additional exits while save/delete is pending, then dispatch only the original action after the operation succeeds.

</details>

<summary>Details</summary>

### Stack removal interception and async redispatch

The `beforeRemove` listeners in `NoteDetailScreen`, `TaskDetailScreen`, and `ProjectDetailScreen` call `event.preventDefault()`, perform either deletion or an update, and redispatch `event.data.action` only after a successful store operation (`NoteDetailScreen.tsx:111-128`, `TaskDetailScreen.tsx:125-140`, `ProjectDetailScreen.tsx:102-116`). React Navigation’s native-stack uses the same core removal-prevention path for the header action, Android back, and gesture removal, so those routes do reach this logic when the record is present. The explicit note/task/project delete handlers set the ref before deleting and then call `goBack()` on success (`NoteDetailScreen.tsx:215-223`, `TaskDetailScreen.tsx:215-226`, `ProjectDetailScreen.tsx:217-226`), and task completion sets it before its successful `goBack()` (`TaskDetailScreen.tsx:222-229`), avoiding a second save/delete for those intentional actions.

The guard is not mutually exclusive while the async operation is in flight. Each listener begins with `if (!record || handlingBackRef.current) return`; after the first event sets the ref, a second header tap, Android back press, or gesture can therefore proceed without `preventDefault()`. The screen can disappear before the first delete/save finishes, leaving a failed operation’s error Snackbar unmounted; if the first operation later redispatches its saved action, that action is also being dispatched after the user has already left the screen (**confirmed**). Keep the route prevented until the pending operation resolves, or use a separate “internal navigation dispatch” token rather than treating all subsequent events as already handled.

The task completion path’s immediate navigation without an explicit `saveTask()` flush is pre-existing from commit `0adbdb7` (the current change only adds the guard flag around `goBack()`). It is not attributed to this back-out change, but it remains a separate preservation gap if explicit completion is intended to save edits made within the one-second debounce window.

### Blank predicates delete records with other edits

`NoteDetailScreen`’s new back predicate only checks `titleRef`, `bodyRef`, and whether a list note has any list items (`NoteDetailScreen.tsx:117-122`). It does not include `projectIDRef`, `noteType`, `pinned`, or `archived`. For example, creating a blank note, assigning it to a project through `handleProjectChange`, and immediately backing out takes the delete branch even though the project assignment was a persisted edit. Switching a blank note between text and checklist can have the same result when no list item remains. The explicit `isNoteBlank` dialog helper has the same content-only definition (`NoteDetailScreen.tsx:225`), so the UI’s warning also describes these edited notes as empty (**confirmed**). Include every persisted field in the dirty comparison, or do not delete once any non-content field has changed.

`TaskDetailScreen`’s `isTaskBlank` checks only title and body (`TaskDetailScreen.tsx:231`), while the editor can persist `projectID`, due date/time, recurrence settings, and separate subtasks through the task store. A new task with a due date, project, recurrence option, or subtask but no title/body is therefore deleted by every guarded back route (`TaskDetailScreen.tsx:132-135`), and an existing title-less task with those fields is also at risk. Compare all task fields and the current subtask set before taking the delete branch (**confirmed**).

`ProjectDetailScreen`’s predicate covers the project’s only editable scalar fields and checks active, shared, archived notes plus tasks (`ProjectDetailScreen.tsx:91-99`). Its content check prevents an empty-looking project containing a linked record from being deleted; the primary blank-detection gap is therefore in note/task metadata rather than an omitted project field.

### New-record visibility and untouched-item cleanup

The top-level add handlers create a record and navigate immediately: `NotesListScreen.onAdd` (`NotesListScreen.tsx:61-65`), `TasksListScreen.onAdd` (`TasksListScreen.tsx:59-63`), and `ProjectsListScreen.onAdd` (`ProjectsListScreen.tsx:45-49`). The core stores write the Legend observables synchronously but project them into the React-facing arrays in `requestAnimationFrame` callbacks (`noteStore.ts:526-529`, `taskStore.ts:422-425`, `projectStore.ts:269-272`). If the user backs out before that projection runs, each detail guard’s `if (!note || handlingBackRef.current) return` / equivalent (`NoteDetailScreen.tsx:112`, `TaskDetailScreen.tsx:127`, `ProjectDetailScreen.tsx:103`) permits removal without invoking delete. The newly created blank record remains in the observable and can later appear in the list (**likely**).

`ProjectDetailScreen` already applies a `waitForStoreRecord` loop for its own note/task add buttons (`ProjectDetailScreen.tsx:179-195`), which shows the intended mitigation but leaves the list-level paths inconsistent. Apply the same visibility handshake to all three list add handlers, or make the detail screen treat a missing record as a pending load and block back until it can decide whether to delete it.

</details>
