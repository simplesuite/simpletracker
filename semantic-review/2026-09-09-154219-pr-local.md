# Project detail links and mobile settings

The mobile change fills the Settings tab with account and appearance controls and expands project details into linked note/task views. Project records are filtered from the core stores, cards and list rows route into the Notes and Tasks nested stacks, and task checkboxes call the existing complete/reopen actions. The theme choice is persisted in AsyncStorage and the tab param types now describe nested navigator params. Watch for: the new add flows navigate before the store bridge exposes the created record (**confirmed**), shared-project task creation can open an unsaved phantom editor (**confirmed**), and system appearance changes are not observed after the initial snapshot (**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

Immediate navigation after project-scoped creation interacts badly with the animation-frame-backed store bridge and can remove the project association during detail autosave (**confirmed**). The nested tab-to-stack route shape itself is type-safe, but the add behavior needs to account for the destination screen’s initial store snapshot.

The project screen does not surface action failures, and its Add task button can route to a record that was never stored for an offline shared project (**confirmed**).

The new `system` option samples `Appearance` rather than subscribing to it, and asynchronous preference restoration can overwrite a choice made before hydration finishes (**confirmed**, **likely**).

## Details

### Project-scoped creation loses the link during immediate nested navigation

`ProjectDetailScreen` creates a note or task with the project ID and immediately navigates to its sibling stack (`ProjectDetailScreen.tsx:120-127`). Core writes the record to a Legend observable, but the React-facing Zustand arrays are projected on `requestAnimationFrame`; the destination detail screen can therefore mount while its `note`/`task` selector is still undefined. Both existing detail screens initialize their local `projectID` only from that first render and do not hydrate it when the record later appears. Once the selector updates, their debounce starts and saves the still-empty local project ID, changing the newly created record back to an unlinked item (**confirmed**).

This breaks the central “add from a project” behavior even when creation succeeds: the new item opens, but after the autosave it no longer appears under the project. Make the creation route wait for the record to be visible, or pass the known project ID through the route and hydrate the detail form when the record becomes available; the latter must avoid overwriting user edits.

### Shared offline Add task opens a phantom editor

`addTask` always calls `openTask(task.recordID)` after `createBlankTask(id)` returns (`ProjectDetailScreen.tsx:125-127`). The core action deliberately returns a task-shaped value for a shared project while offline but does not write it to `tasks$` (`taskStore.ts:148-155`). `TaskDetailScreen` has no matching task to autosave, yet it still renders an editor, so the user can enter data and leave without any persisted task (**confirmed**).

The project screen should not navigate unless the returned ID is present in the task store, and should surface the store error or an explicit “shared project requires a connection” message. The same failure path for notes is silently ignored because `addNote` only opens when the result is non-null (`ProjectDetailScreen.tsx:120-123`), leaving the Add note button with no feedback in that state (**confirmed**). The checkbox handlers likewise ignore failed completion/reopen results, so shared offline task actions appear to do nothing (**confirmed**).

### System theme is a one-time sample rather than a live mode

`getSystemTheme` calls `Appearance.getColorScheme()` and `setThemeMode('system')` stores that single result (`themeStore.ts:13-23`). There is no `Appearance.addChangeListener`, so after selecting “Use system setting,” changing the OS appearance while the app is open leaves `effectiveTheme` and the Paper provider on the old theme until another explicit store update or reload (**confirmed**). Add an appearance listener that updates only `effectiveTheme` while `themeMode` remains `system`, and remove it when the store is torn down if the implementation is mounted rather than module-scoped.

### Async preference hydration can overwrite a fresh selection

The module starts `AsyncStorage.getItem('themeMode')` without a hydration guard and later calls `setThemeMode(saved)` (`themeStore.ts:30-35`). If the Settings radio group is changed before that read resolves, the stale persisted value wins and the UI visibly jumps back to the previous preference (**likely**). Track hydration/user-write ordering or load the preference before accepting a selection; persistence failures should remain best effort, but must not make a newer in-memory choice lose.

### New behavioral paths have no mobile coverage

The mobile package has no tests beyond a script that exits successfully without running tests. There is therefore no automated coverage for nested tab-to-stack navigation, project-scoped creation preserving `projectID`, the completed-task disclosure/reopen path, or theme hydration/system changes (**confirmed**). Add focused screen/store integration coverage before relying on this behavior in release validation.
